# Full question-bank offline download

Source implementation added 2026-10-09; compilation, device and live-backend checks remain pending.

## User flow

While signed in online with both `tests.start` and `tests.download_full_bank`, open **Offline practice → Download full question bank** and confirm. The app downloads all caller-visible, downloadable questions into ordinary offline practice batches, including answer/explanation/translation/case snapshots and supported bundled question images. It uses the current server/account; this is not an administrator database backup and contains no other users' accounts or server settings.

Progress shows questions saved during this pass, the initial visible count and exclusions. **Pause download** stops further work; **Resume full-bank download** explicitly resumes from the committed cursor/pending IDs. Already saved batches can be studied after an interruption. Restarting the app never automatically resumes network requests or uploads practice results. Downloaded practice remains available to the last bound account on the same authenticated local server profile after the online login expires. The startup/recovery/sign-in screens offer **Study downloaded material offline** when material is retained; this opens local-only practice without downloads or result uploads. Online actions require a fresh login.

The server excludes questions protected by unfinished closed-book ordinary/master exams. Pack generation independently rechecks visibility, protection and grading readiness. A batch rejected for size/content is split into smaller read-only snapshot requests; a single question that cannot be downloaded is counted as skipped. Network/authorization/server failures stop the operation and preserve the checkpoint. A finished pass with skipped material is not a claim that every question was downloaded.

Existing packs, answers and pending completions are kept. Starting another completed-bank download adds fresh snapshots; it does not overwrite older packs. Deleting a pack explicitly removes that local material, so download counters describe what was saved during the pass, not the current retained database size. Content/access can change during a pass: the highest initial visible question ID bounds additions, while each page/pack checks current access; this is not an atomic database snapshot. The UI reports count differences, but unchanged counts cannot establish unchanged content.

## Contracts and limits

- New read-only `GET /api/v1/exam/offline/catalog/?after=...&upper_bound=...`: `tests.download_full_bank` plus an independent `tests.start` check, `visible_to(request.user)`, ascending ID keyset pagination. Returns `question_ids`, `upper_bound`, nullable `next_after`, `total` and page `excluded` count. The catalogue itself remains read-only; matching learning/grant schema is now required by pack/completion processing.
- Snapshot `POST /exam/offline/packs/` remains the pack authority and now records idempotent per-user/question grants; bulk requests send `full_bank: true` and independently require `tests.download_full_bank` in addition to `tests.start`; it does not create a server session or completion. Catalogue reads and retry-safe snapshot/grant issuance can be split/repeated by the bulk downloader. Ordinary uncertain writes are never replayed.
- Explicit `POST /exam/offline/completions/` retains frozen UUID/body and durable receipts. New material freezes occurrence/answer timestamps anchored to signed pack issue time; legacy pending bodies omit the new fields. Matching deployed completion schema is still required for synchronization.
- Per pack: the server's configured question limit capped at 200, existing 4 MiB response/material limit and 1 MiB individual-image limit. Oversized/inaccessible/unready single questions remain excluded rather than leaking protected data or bypassing limits.
- The former five-pack/8 MiB aggregate preference limit is removed. Device free space bounds the bank; storage reserves 16 MiB and caps each serialized local practice material at 16 MiB, including its answers/results. New-download capacity rejection preserves existing progress and the earlier checkpoint.

## Local persistence

Offline packs use immutable `EncryptedFile` files under the application's no-backup directory, scoped to the stable local server profile. The encrypted account preferences hold only the authenticated pack index/small display summaries, content checksums and bank-download checkpoint. The UI loads full payload/images only when opening a batch; bank download holds one returned batch at a time. Storage work runs on IO coroutines, with synchronous busy guards preventing conflicting actions.

File bytes are encrypted, closed and synced before one preference commit publishes both index and download checkpoint. Old files/legacy preference material stay available until the new index commits; pre-commit aborted staging files are removed, while a failed/uncertain commit retains both generations for explicit storage Retry. Successful writes clean unreferenced encrypted files. Retries reuse immutable content with the same checksum. A missing/corrupt payload fails that batch's opening without hiding other readable summaries.

Legacy encrypted `offline_material` is still readable and moves to file storage on its first successful write, preserving pack tokens, answers, navigation, completion UUID/body and synchronized results. Ordinary online-session expiry retains encrypted downloads, offline answers, pending completions and recovery while locking online drafts/actions. Offline access has no separate time limit; explicit logout, a different authenticated account/UUID, or a confirmed `ACCOUNT_EXPIRED` response still revoke access and clear the current profile's private storage. Logout/account-expiry also durably mark the profile as requiring authentication before cleanup, so retained files after a cleanup failure remain gated. Server address changes retain files and require reauthentication as previously approved. Generic missing-session responses cannot distinguish elapsed session lifetime from server-side session revocation/account deactivation; they permit local-only retained study, never online access. No plaintext temporary copies or document exports are created. Files already erased by an older app cannot be recovered by this change; sign in and download again.

## Per-user full-bank permission

Administrators with `admin.permissions` can open **Permissions → Users**, select a member/moderator and find **tests.download_full_bank** under **Tests & study**. Set **Allow / Force on** to grant it or **Deny / Force off** to revoke it, then save. **Inherit** follows the role matrix. Default role configuration grants the capability to moderators and leaves it off for members. Per-user denial still overrides a moderator role grant. Existing saved RoleCapabilities rows remain authoritative: if a deployed moderator role predates this default, enable it once in **Permissions → Roles → Moderator** and save; a source-default change does not overwrite customized database role settings. Administrators retain the existing policy of holding every capability; their access cannot be removed with user overrides.

Android obtains fresh account capabilities when opening online Offline practice and through **Refresh download permission**, so administrators can grant/revoke this feature without requiring the learner to log out and lose local files. A failed permission read disables the bulk action while leaving cached packs usable. Start/Resume and their ViewModel handlers require the current grant. Server 401/403 during a bulk request stops the download and disables further Start/Resume until a fresh permission check succeeds. Catalogue and each marked bulk pack request independently enforce grants at the server; an already authorized in-flight response may finish while an administrator changes permissions.

This capability controls the full-bank feature. Selected-question downloads and explicit completion synchronization retain `tests.start`. Revocation does not delete already downloaded packs, and it cannot remotely erase files from a device that is offline. The account-expiry/logout/isolation rules above remain in force. Adding this registry capability needs a matching backend reload and no migration, seeding or database setup; existing role/user JSON editors recognize it from the catalogue.

## Learning consistency and selected-download budget

Matching backend now uses durable learning/exposure/grant records; see [implementation/schema contract](../../../backend/docs/contracts/learningConsistency.md). Selected downloads still require tests.start, with a cumulative server-enforced budget of 200 distinct question IDs without tests.download_full_bank. Re-downloads of already granted IDs remain allowed. Clearing a client cache or omitting full_bank does not reset the budget. Capability holders can download the entire accessible bank; revocation does not delete local files or prevent otherwise authorized completion synchronization.

New packs include signed issued_at. Android retains a server clock offset and freezes per-answer/completion timestamps in encrypted material before upload. Retry never changes those fields, completion UUID or elapsed duration. Delayed learning is replayed chronologically on the server and credited on occurrence days; invalid clock bounds fail while preserving pending material. Legacy material uses receipt-day chronology because its original timestamps were not sent. No database initialization, migration action, build or device verification was performed by the agent.

## 2026-10-13 focused packs, text-only material, updates and review

The existing full-bank grant (`tests.download_full_bank` plus `tests.start`) also gates focused catalogue downloads by exact book title, category IDs and tag names. Blank filters mean the whole visible bank; combined book/category/tag filters reuse production question filtering. Catalogue pages echo their selection, and Android verifies the echo. The checkpoint freezes selection and image inclusion across pause/restart; resetting a paused checkpoint keeps saved packs while allowing new filters. Each marked pack still independently checks permissions, visibility, closed-exam answer withholding and grading readiness. The original selected-ID download budget is unchanged.

Pack requests accept optional `include_images` (default true). Text-only packs omit image bytes and return `image_question_ids` so missing images are labelled explicitly. `images_included` is checked against the requested setting; older backends cannot silently claim to supply text-only packs. Signed grading snapshots, byte ceilings and learning grants remain. Pack responses carry a stable content revision derived from snapshot content. Check for an updated copy reissues the same owned/visible IDs with the original image setting, compares revision/content, and saves changed material as a separate new pack. Old pack tokens, navigation, answers and frozen completions remain intact. Existing completion freshness checks can still reject changed or unavailable learning content; retaining the old pack is not a promise that stale learning will be accepted.

Finished packs expose explicit offline review, using the stored answers/keys/explanations before synchronization. Completion uploads use per-pack activity/error state rather than the screen-wide busy flag; another cached pack can be opened, answered and navigated during an upload. Immutable completion UUID/body/time remain the receipt identity. Local commits and payload opening are serialized; upload confirmation merges into the latest material so current navigation and other packs' answers survive. The uploading pack cannot be deleted/restarted, and storage failure still blocks new answers until recovery. Downloads/refreshes do not race active uploads.

Backend-first rollout is required for filtered catalogue echoes and optional-image/revision fields. Changes are additive and require no new database fields; existing learning/grant/receipt schema readiness is unchanged. Source checks do not establish device/network/receipt concurrency.
